# 起因

在日常维护[项目](https://blog.3mua.cn/post/1791444617263/)时发现某个接口返回403

最初以为业务流程改变，所以进行了分析。

发现即使登陆流程完全同步，其接口返回的依然为403

# 复现

原流程是通过某个接口获取带有Location响应头的内容，再通过访问这个Location获取Cookie

但今天在访问Location后并未返回任何Cookie？！

最初以为前置Cookie没有做到位，导致访问此Location的时候未返回有效内容，于是检查前置Cookie后依然未实际返回。

:::note[为什么会这么认为]
在请求后会返回403，所以我认为是Cookie鉴权导致的
:::

但经过逐渐排查依旧无任何进展。

但此时我将Location放入POSTMAN请求依然可以正常访问，即使错误也是按照JSON格式返回的200，而并非403错误HTML页面。

同时也能发现无论是否带有Cookie都会返回SET-COOKIE的响应头。

我又使用CURL访问，依然与POSTMAN相同。

这是为什么？我怀疑过是否为HTTP/1.0的问题，因为在近期对于小黑盒的研究中发现：小黑盒需要使用HTTP/2.0请求。不过使用CURL -v后发现其依然为1.0协议。

但诡异的是先前的接口都可以访问，只有这个接口无法访问。

# 原因

经过排查后发现是`User-Agent`的问题

我先前一直认为Go的HTTP请求是默认无User-Agent头的...

但搜索发现Go会默认携带 **Go-http-client/1.1** 的请求头，而今天主业务接口增加了防火墙检测UA，导致无法访问...

同时我也测试了Python的默认请求头，也是无法访问的...

但奇怪的是POSTMAN请求头是可以访问的

看来下次要注意UA的问题了，不要想着当时不检测就不修改。

##　为什么先前接口可以访问？

在事后发现先前接口均为单点登陆系统的接口，而并非实际的业务接口

其实当时我考虑过UA的问题，不过当时修改为请求单点登陆接口的UA了...
